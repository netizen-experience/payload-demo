# Migration plan: AWS (SST/OpenNext) → Vercel Hobby

**Status**: Migration complete. All 5 phases executed and verified — `payload-demo.netizenexperience.com` is live on Vercel (Neon + Blob), 4/4 Playwright green against the production domain, and the AWS stack has been fully torn down (`sst remove` succeeded). Executed on the `migrate-to-vercel-hobby` branch (forked from `migrate-to-serverless`), which is now the Vercel project's Production branch.

## Why

The AWS serverless setup (this branch, fully working) has a real fixed monthly cost floor of roughly **$25-30/month regardless of traffic**, dominated by two VPC Interface endpoints (Secrets Manager + SQS) that exist *purely* so Lambda can reach Aurora privately. Lambda itself, Aurora's ACU-hours, CloudFront, and S3 are all cheap-to-free at this site's actual (low/spiky) traffic — the VPC is the expensive part, and it exists only because of the "private database" networking requirement.

Vercel Hobby (free tier) + a managed Postgres provider (Neon/Supabase, also free-tier) eliminates that VPC requirement entirely: Vercel's serverless functions reach the database over the public internet, no private networking needed. The client for this project isn't being charged (explicitly confirmed by the user), so Vercel Hobby's non-commercial-use restriction is a non-issue here.

This is a genuinely low-effort migration compared to switching CMS platforms (Sanity/Contentful/etc., discussed and rejected earlier) — **Payload itself doesn't change at all**, only the hosting target. The original Payload website template this project is built from was actually designed with Vercel in mind (see "Already-present Vercel awareness" below) — today's AWS/SST work was a deliberate detour to demonstrate/exercise a different deployment pattern, not a sign that Vercel wouldn't work.

## Load-bearing technical context from the AWS work

These are things learned the hard way this session that should directly inform (or be re-verified against) the Vercel plan — not just "for the record."

### Things that were AWS/Lambda-specific and likely don't apply on Vercel (re-verify, don't assume fixed)

- **Next.js 16 → 15.4.11 downgrade**: caused by Turbopack (mandatory in Next 16's `next build`) hashing `sharp`'s native binary with random suffixes, breaking **Lambda** cold-start module resolution under **OpenNext**. This was specifically about OpenNext's Lambda bundling, not Next.js itself. Vercel is Next.js's own platform and handles native module bundling through a completely different pipeline — **Next 16 may well be fine on Vercel**. Worth actively re-testing rather than assuming the downgrade must persist. Full compatibility checklist either way: `docs/nextjs-version-compatibility.md`.
- **The entire image-loading saga** (relative-vs-absolute media URLs, `remotePatterns` allowlist, `NEXT_PUBLIC_SERVER_URL` chicken-and-egg, image-optimizer IAM permissions) was fundamentally about OpenNext's Lambda image-optimizer having exactly two paths for a `next/image` src (absolute URL → HTTP fetch, anything relative → S3 key lookup, no fallback) — this is an **OpenNext** implementation detail, not a Next.js one. Vercel has **native, first-party** image optimization for `next/image` with no equivalent split. The current code (`src/utilities/getMediaUrl.ts` always returning absolute URLs, `next.config.ts`'s `remotePatterns`) will likely still work fine on Vercel (absolute URLs are always safe), but the *reason* it was necessary won't exist there — don't be surprised if it turns out to be unnecessary complexity in hindsight.
- **`payload.db.migrate()` failing inside the migrate Lambda specifically** (`ERR_REQUIRE_ESM` loading dynamically-imported `.ts` migration files — confirmed the *exact same call* works fine locally on the same Node version) was never root-caused; documented as a known-broken, non-fatal-by-design workaround in `infra/migrate-handler.ts`. This whole mechanism (a dedicated VPC-attached Lambda just to reach a private database) goes away entirely on Vercel — migrations would run some other way (Vercel build step, or a plain script run against a publicly-reachable Neon/Supabase instance from a local machine or CI). This bug is very unlikely to resurface, but if something *does* look like ESM/CJS interop weirdness when running migrations post-migration, this is the precedent to remember.
- **Lambda's 6MB synchronous response/request payload limit** drove re-encoding the seed dish photos from 7-8.5MB PNGs to ~0.25-0.4MB JPEGs (`scripts/optimize-seed-photos.ts`). Vercel's own function body-size cap is 4.5MB (confirmed, a separate limit, still current) — the re-encoded photos (all under 1MB) comfortably clear this too, so no new work needed, just note the reason changes slightly. This same 278MB-total media library is also what makes Vercel Blob's 1GB free tier viable now (see Decisions below) — it would not have fit before this re-encoding.

### Things that are genuinely platform-independent and carry over as-is

- **Jobs queue / scheduled publishing removal** — an app-level product decision (nobody used it), unrelated to hosting platform. Stays removed.
- **`dangerouslyAllowSVG` / SVGs rendered `unoptimized`** — a Next.js framework-level default (XSS safeguard), not an OpenNext or AWS thing. Applies identically on Vercel.
- **Local dev workflow, Payload collections/config, seed script, DB schema/migrations** — none of this changes. Payload itself is completely portable; only its `db` adapter's connection string and the `storage-s3` plugin's credential source change.
- **The `scripts/export-local-db-for-staging.ts` + `infra/db-restore.ts` pair** (topological-sort-aware, enum-safety-checked table restore, built for pushing local Postgres into a VPC-private Aurora via Lambda) is **directly reusable, and much simpler to use**, for seeding a new Neon/Supabase database — since that target is publicly reachable, you can skip the whole "export to S3, invoke a Lambda, have the Lambda read it back" dance and just connect `pg.Client` directly from a local script. The restore logic in `infra/db-restore.ts` (truncate + FK-safe reload + sequence reset) is the reusable core; only the transport mechanism simplifies.

### Already-present Vercel awareness in this codebase

Not something built this session — pre-existing in the template, but directly relevant:
- `next.config.ts` and `src/utilities/getURL.ts` both already check `process.env.VERCEL_PROJECT_PRODUCTION_URL` as a first-class case (falls back to it before other env vars). Vercel sets this automatically at both build and runtime — meaning the `NEXT_PUBLIC_SERVER_URL` chicken-and-egg problem that required hardcoding the CloudFront domain in `sst.config.ts` **may not need any manual domain-hardcoding at all on Vercel** — worth confirming this resolves automatically before porting over any of that hardcoding.

## Decisions (resolved — reasoning kept so it doesn't need re-litigating at execution time)

- **Postgres: Neon**, not Supabase. Neon has native Vercel Marketplace integration (auto-injects connection env vars, can branch a database per preview deployment) and scales-to-zero with ~500ms-2s cold resume — a strict improvement over Aurora's observed 10-55s. Supabase's free tier fully **pauses after 7 days of inactivity and requires a human to manually unpause it via their dashboard** — a categorically worse failure mode than Aurora ever had, for a site that could plausibly go quiet for a week. (Numeric specifics are provider-published and change without notice — re-verify against Neon's current pricing page at signup, don't treat them as locked in.)
- **Media: Vercel Blob**, not S3. `@payloadcms/storage-vercel-blob` is an official Payload plugin (same lineage as `storage-s3` already in use). Confirmed config API: `vercelBlobStorage({ collections: { media: true }, token: process.env.BLOB_READ_WRITE_TOKEN })`. Current total media is **278MB** (confirmed via `aws s3 ls --summarize`) — comfortably inside Blob's 1GB Hobby free tier (10GB transfer/month), which is only true because of the photo re-encoding work already done. Switching removes AWS from the Vercel deployment entirely — no OIDC, no IAM role trust policy, no static keys, no ongoing AWS bill for media. `BLOB_READ_WRITE_TOKEN` is auto-injected by Vercel when the store is added to the project. Real risk to know: Hobby's Blob store **pauses** (not billed overage) if the free limits are exceeded — a hard failure, not a gentle one; unlikely at this traffic level but worth monitoring if the media library grows.
  - Blob URLs are **public and absolute** (`https://<store-id>.public.blob.vercel-storage.com/<filename>`), unlike S3's proxied `/api/media/file/...` pattern — this actually simplifies the AWS-era `getMediaUrl`/`remotePatterns` situation rather than complicating it. `next.config.ts`'s `remotePatterns` will need to allow this Blob domain.
- **Next.js 16 upgrade: explicitly out of scope for this migration.** Conflating "did the hosting move break something" with "did the framework upgrade break something" makes root-causing either one harder. Revisit as its own follow-up once Vercel is stable — `docs/nextjs-version-compatibility.md` already has the re-check procedure ready.
- **Domain cutover: direct, no rehearsal subdomain.** Once a Vercel preview deployment is fully validated (Playwright green, no CORS issues — see risk below), assign the real custom domain and flip DNS in one step. Acceptable given this is a demo with no real downtime cost.
- **A real risk not present in the AWS setup, found during planning**: `getServerSideURL()`/`getClientSideURL()` (`src/utilities/getURL.ts`) fall back to `VERCEL_PROJECT_PRODUCTION_URL`, which resolves to the *production* domain even when testing a *preview* deployment's own unique URL. Three consumers: `payload.config.ts`'s `cors: [getServerSideURL()]`, `plugins/index.ts`'s SEO `generateURL`, and `next.config.ts`'s `remotePatterns` (baked at build time). If a preview's actual browser origin differs from the resolved production hostname, Payload's CORS allowlist may reject the preview's own admin/API calls. **Explicitly check the browser console for CORS errors on the preview URL's `/admin/login`** during execution — don't just check that pages render.

## Phased execution plan

**Phase 1 — Provision Neon + Vercel project shell** ✅ Done
Neon connected via Vercel's account-level Storage tab (`neon-bole-lamp` store, Neon project id `young-sea-28373352`), Vercel Project created by importing the GitHub repo and tracking `migrate-to-vercel-hobby`, Blob store added (had to be recreated as public — see Phase 3 gotcha below). **Phase 2 — Migrate database to Neon** ✅ Done
Ran `npx payload migrate` against Neon's unpooled connection string to create the schema, then `scripts/export-and-restore-to-neon.ts` (new script, combines `scripts/export-local-db-for-staging.ts`'s export query with `infra/db-restore.ts`'s `restoreDatabase()`, connected directly via `pg.Client` — no S3/Lambda hop needed) to copy all local data over. All 90 tables matched source/target row counts, zero warnings. Neon's TLS cert is publicly trusted — no `sslmode=no-verify` workaround needed, plain `sslmode=require` from Neon's own connection string works. Verified with `npm run dev` locally against Neon end-to-end.

**Phase 3 — Migrate media to Vercel Blob** ✅ Done
Swapped `s3Storage` for `vercelBlobStorage` in `src/plugins/index.ts`, with `disablePayloadAccessControl: true` on the collection (needed to get Blob's own absolute URLs instead of Payload's `/api/media/file` proxy — not automatic, has to be set explicitly). New script `scripts/migrate-media-to-blob.ts` copied all 272 objects (278MB) from S3 to Blob and updated every `media` row's `url`/`sizes_*_url` columns in Neon, zero mismatches. Added the Blob domain to `next.config.ts`'s `remotePatterns`.
- **Gotcha**: Vercel now defaults new Blob stores to **private access**, and access mode is permanent per store (can't change after creation) — had to delete the first store and recreate explicitly as public. Not something the original plan anticipated; a recent platform default change.

**Phase 4 — Deploy to Vercel, re-verify behavior, re-point Playwright** ✅ Done, 4/4 Playwright green
Confirmed: `NEXT_PUBLIC_SERVER_URL` genuinely doesn't need manual hardcoding — `VERCEL_PROJECT_PRODUCTION_URL`'s existing fallback was sufficient, unlike AWS's chicken-and-egg problem. Several real issues surfaced and fixed along the way (see "Findings from execution" below); once resolved, `tests/e2e-staging/smoke.e2e.spec.ts` re-pointed at the Vercel preview URL with zero code changes to the test itself, as expected (env-driven).

**Phase 5 — Custom domain cutover + AWS decommission** ✅ Done
Changed the Vercel Project's Production Branch to `migrate-to-vercel-hobby` (Settings → **Environments**, not Git — Vercel relocated this setting), added `payload-demo.netizenexperience.com` as a domain, promoted the already-built Preview deployment to Production (no rebuild needed, though Vercel triggered one anyway since Production/Preview env var scopes differ), then manually updated DNS in the domain's own DNS panel to point at Vercel — bypassing the old delegated Route53 subdomain zone entirely rather than flipping records within it (see finding below). 4/4 Playwright green against the live domain. Then `npx sst remove --stage staging` — succeeded (`✓ Removed`) after ~10 rounds of IAM permission gaps (see findings). Manually deleted the pre-existing, non-SST-managed `payload-demo-media-263078047633` S3 bucket (272 objects, 278MB, already fully migrated to Blob). The now-inert Route53 subdomain zone `Z06693953EJ4NP2ZAD3IE` was left for the user to delete directly. AWS Cost Explorer check (confirm the cost floor actually drops) is the one open follow-up, left to the user to check in a day or two. `sst.config.ts`/`infra/`/AWS-specific scripts stay in git history, non-load-bearing, not deleted.
- **Resolved**: the Neon `preview/migrate-to-vercel` branch vs `main` divergence (flagged as a risk after Phase 4) surfaced concretely during Phase 5 — Production reading from `main` after promotion caused a Blob upload collision (see finding below) precisely because `main`'s own DB history didn't match Blob's actual shared-namespace state. Left as-is rather than disabling Neon's per-branch-preview feature outright; worth reconsidering if this recurs.

## Findings from execution (Phases 1-5) — not anticipated in the original plan

- **`tsconfig.json`'s `**/*.ts` include scope catches everything, not just the app**: `next build`'s type-check walks the whole repo per tsconfig, including AWS-era files never imported by the Next.js app. Two build failures came from this: `infra/migrate-handler.ts` needing `@aws-sdk/client-s3` (removed with `--no-save` while testing the media-transfer script, which masked it locally), and `sst.config.ts`'s `/// <reference path="./.sst/platform/config.d.ts" />` (a locally-generated, gitignored file that never exists on a fresh checkout — local testing was masked by a stale `.sst/` directory from prior SST usage). Fixed by restoring `@aws-sdk/client-s3` as a real dependency and adding `sst.config.ts` to tsconfig's `exclude`. Lesson: verify any `--no-save` install doesn't hide a real compile-time dependency, and test builds from a genuinely fresh `git clone`, not just `npm ci` in place (gitignored generated directories survive `npm ci`).
- **Vercel Deployment Protection blocks Preview URLs by default** — a separate Vercel-SSO wall in front of the app itself, unrelated to app code. Had to be disabled (Project Settings → Deployment Protection) before either manual verification or Playwright could reach the deployment at all.
- **Connecting a Storage resource to a Project doesn't always reliably wire its env var into that Project** — the Blob store's token existed in the store's own dashboard/Quickstart tab but wasn't actually live in the Project's Environment Variables until added there explicitly, causing `vercelBlobStorage` to silently disable itself and fall back to Payload's local-storage proxy behavior (per its own documented behavior when `token` is unset/invalid) — no error, just wrong URLs.
- **CORS**: `payload.config.ts`'s `cors: [getServerSideURL()]` only ever resolves to the production domain on Vercel (via `VERCEL_PROJECT_PRODUCTION_URL`), which rejects a preview deployment's own browser origin — confirmed via curl (no `access-control-allow-origin` header at all for the preview's own origin). Fixed by adding `VERCEL_URL` (current deployment) and `VERCEL_BRANCH_URL` (stable per-branch alias) to the allowlist.
- **Admin thumbnail 500s with `disablePayloadAccessControl: true`**: Payload core's auto-computed `thumbnailURL` field always points at the internal `/api/media/file` proxy regardless of storage adapter — a known inconsistency with the plain `url`/`sizes.*.url` fields (this proxy route errors once access control is disabled on the adapter). Fixed via `adminThumbnail` as a function on the Media collection, reading `doc.sizes.thumbnail.url` directly instead of relying on the broken field.
- **Neon's per-branch database for Preview deployments** (see Phase 5 note above) — a real Neon/Vercel integration feature, not a bug, but easy to miss since the Vercel dashboard's Environment Variables page shows one `DATABASE_URL` value regardless of environment even though it resolves to a different physical database per branch.
- **Vercel's Production Branch setting moved to Settings → Environments**, not Settings → Git where it used to live and where the docs/community threads often still point. Changing it doesn't retroactively promote an already-built Preview deployment — that needs a separate explicit "Promote to Production" action (Deployments tab → "…" menu), which is instant (no rebuild) *unless* Production/Preview env var scopes differ, in which case Vercel rebuilds anyway.
- **Vercel Deployment Protection and a stale Blob token compounded on the first Preview**, then a **third, unrelated bug appeared on Production specifically**: uploading via `/api/media` 500'd with "this blob already exists." Root cause: Payload's filename-uniqueness check only queries its own DB (Production's `main` Neon branch), but Vercel Blob is one global namespace shared across every Neon branch — a filename already written by an earlier Preview-branch test looked "free" to Production's DB but wasn't free in Blob. Tried fixing with `addRandomSuffix: true`, which exposed a **confirmed upstream bug** in `@payloadcms/storage-vercel-blob` (`handleUpload` mutates one shared object across every parallel image-size upload, so whichever size resolves last clobbers the top-level `filename`/`url` fields with a mismatched value). Reverted — the collision only happens with cross-branch reuse of an identical filename bypassing normal cleanup (real uploads and Playwright's own `afterAll` don't hit this), so it wasn't worth carrying a known-buggy plugin option for.
- **The Route53 zone `Z06693953EJ4NP2ZAD3IE` was a *delegated subdomain zone*** for `payload-demo.netizenexperience.com` specifically (its own NS/SOA records prove this), separate from the parent `netizenexperience.com` zone. The domain cutover moved the actual A/CNAME record into the *parent* zone directly rather than flipping records inside this delegated zone — meaning when `sst remove` later deleted the old CloudFront-pointing A/AAAA records *inside* this now-bypassed zone, it had zero effect on the live site. Worth double-checking DNS architecture like this before assuming "delete the zone SST used" is safe — in a different setup it could have taken the live site down.
- **`sst remove --stage staging` hit roughly ten rounds of missing IAM permissions** before succeeding — this "Developers" permission set was scoped incrementally during the original *deploy*, and teardown exercises a mostly-disjoint set of delete/list actions deploy never needed: `cloudfront-keyvaluestore:*` (a separate IAM namespace from `cloudfront:*` — the existing grant only covered creating/deleting the *store*, not its keys), `lambda:*FunctionUrlConfig`, `iam:ListInstanceProfilesForRole` (required before deleting a role, even though the role has no instance profiles), `logs:DeleteLogGroup` against log groups with `MyWeb*`/`sta-*` prefixes (SST's internal Pulumi component names, not the `payload-demo-staging-*` prefix the original policy assumed), `servicediscovery:DeleteNamespace`, and `cloudfront:*CachePolicy`. All added to `infra/developers-compute.json`, comfortably under IAM's 6144-char inline-policy limit throughout (ended at ~5550 chars). Left in place rather than trimmed back post-teardown.
